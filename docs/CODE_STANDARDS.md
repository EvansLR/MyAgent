# MyAgent 代码与协作规范

## 文档优先

任何代码实现之前，先有文档。

这不是形式主义，而是为了保证每次开发都有清晰方向：

- 先说明模块要解决什么问题。
- 再说明第一阶段做什么、不做什么。
- 最后再写代码。

如果实现过程中发现设计不合适，先更新文档，再调整代码。

## 模块单独设计

每个核心模块都要有自己的设计文档，放在：

```text
docs/modules/
```

例如：

- `MEMORY.md`
- `SKILLS.md`
- `MCP.md`
- `SUBAGENT.md`

模块文档至少要说明：

- 模块职责
- 为什么需要它
- 输入输出
- 核心接口
- 与其他模块的关系
- 第一阶段范围
- 暂不实现的内容
- 测试方式
- 面试时怎么讲

## 实现后更新文档

每做完一部分代码，都要回到对应模块文档里补充实现说明。

实现说明要帮助人理解代码，而不是只写“完成了某某功能”。

建议补充：

- 新增了哪些文件
- 每个文件的作用
- 关键类和函数怎么协作
- 运行流程是什么
- 如何手动测试
- 自动化测试覆盖了什么
- 当前限制是什么

## 先跑起来，再完善

MyAgent 是学习型、面试型项目，不是生产级上线项目。

当前阶段优先级是：

1. 系统能跑起来。
2. 核心链路能讲清楚。
3. 行为能被测试或手动验证。
4. 后续扩展方向能说明白。

不要一开始追求复杂工程化能力，例如完整权限系统、复杂任务队列、生产级监控、插件市场、分布式部署。

这些内容可以写进“后续扩展方向”，但不要阻塞第一版可运行闭环。

## 保持轻量实现

代码实现要遵守“够用、清楚、可扩展”的原则。

优先选择：

- 小模块
- 明确接口
- 简单数据结构
- 可测试函数
- 能直接解释的实现

避免过早引入：

- 大型抽象层
- 复杂继承体系
- 没有当前使用场景的插件机制
- 过度配置化
- 为未来假设写大量代码

## 模块边界清楚

每个模块只做自己的事。

当前项目的基本边界是：

- CLI Channel 负责用户输入输出。
- MessageBus 负责消息传递。
- AgentLoop 负责主 ReAct 循环。
- ContextBuilder 负责组装 system prompt 和上下文。
- LLM Provider 负责屏蔽模型 API 细节。
- ToolRegistry 负责注册、描述、校验和执行工具。
- Memory 负责保存和召回跨轮信息。
- Skills 负责本地能力说明的扫描和注入。
- MCP 负责接入外部工具。
- Trace 负责记录运行过程。
- SubAgent 后续负责受控任务委托。

写代码时尽量不要让上层模块知道下层太多内部细节。

## 测试标准

测试优先覆盖核心行为，不追求为了覆盖率而测试实现细节。

每个模块至少要回答：

- 正常输入能不能跑通？
- 关键异常能不能被安全处理？
- 和上下游模块的接口是否稳定？

如果某个功能暂时不好自动化测试，就要在文档或最终说明中写清楚手动测试方法。

真实 API、真实网络、真实 MCP server 这类能力尽量不要成为单元测试依赖。

单元测试优先使用：

- fake provider
- fake MCP client
- 项目内临时工作区
- 本地只读文件

## Git 提交规范

Git 提交按模块推进。

流程是：

```text
文档设计 -> 代码实现 -> 测试验证 -> 用户确认 -> Git commit -> Git push
```

约定：

- 不为每个小改动频繁提交。
- 一个模块完成后提交一次。
- 提交前必须等用户确认没问题。
- 提交后同步推送到远程 GitHub 仓库。
- 本地配置、密钥、trace、memory 数据不能提交。

提交信息保持简洁，例如：

```text
docs: design subagent delegation
feat: add task-oriented subagents
fix: handle provider tool response fields
```

## 配置与密钥

本地配置使用 `myagent.json`。

示例配置可以提交，例如：

```text
myagent.example.json
```

真实配置不能提交，尤其是：

- API key
- MCP key
- 本地私有路径
- 真实用户数据

如果需要说明配置方式，写进文档，但不要暴露真实密钥。

## 终端体验

CLI 是当前项目主要入口，所以终端体验要保持清楚。

要求：

- 工具调用时展示状态。
- 状态文案中文友好，例如 `正在调用工具：read_file`。
- 工具名保留英文，方便定位代码和 trace。
- 模型回复支持 Markdown 渲染。
- 输出不要过度花哨，重点是让用户知道系统正在做什么。

## 面试导向

这个项目服务面试场景，所以代码和文档都要能讲。

实现一个模块时，需要能回答：

- 为什么要有这个模块？
- 它解决了什么工程问题？
- 它和上下游怎么连接？
- 当前为什么这样简化？
- 如果要上生产，后续怎么扩展？

如果某个实现“能跑但不好讲”，就说明文档或边界还需要调整。

## 当前阶段不追求的内容

第一阶段暂时不追求：

- 复杂并发调度
- 完整后台任务系统
- 分布式队列
- 完整权限模型
- Web UI
- 多用户隔离
- 生产级日志平台
- 完整 checkpoint/resume
- 向量数据库 RAG

Redis、RabbitMQ、复杂任务队列、SubAgent 并发调度等内容可以作为后续扩展方向记录，但不要影响当前最小可运行版本。

## 一句话原则

MyAgent 的代码规范可以概括为：

> 先文档校准方向，再写最小可运行实现；每个模块边界清楚、测试够用、用户确认后按模块提交，并始终保证这个项目能被讲清楚。
