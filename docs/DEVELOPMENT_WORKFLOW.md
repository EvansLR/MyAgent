# MyAgent 开发协作流程

## 基本原则

MyAgent 的开发顺序是：先文档，后实现；先能跑，再完善；先讲清楚，再考虑扩展。

这个项目主要服务研究生面试场景，不追求生产级完备性。所有模块都应该能回答三个问题：

1. 这个模块解决什么问题？
2. 为什么当前阶段这样设计？
3. 如果以后要做复杂，可以往哪里扩展？

## 每个模块的工作流

每个模块按以下节奏推进：

1. 查阅当前 roadmap、决策文档和模块设计文档。
2. 如发现方向变化，先更新文档。
3. 根据文档实现最小可运行版本。
4. 运行最小验证，包括手动验证或必要的自动化测试。
5. 等用户确认没有问题。
6. 再进行 Git add 和 Git commit。

## Git 约定

当前项目要求使用 Git，但提交节奏按模块推进。

- 一个模块完成后提交一次。
- 不为每个小改动频繁提交。
- 提交前必须确认用户已经测试或认可。
- 如果某个模块后续出现问题，可以按模块回退。

建议提交信息格式：

```text
docs: establish project workflow
feat: add message bus
feat: add cli channel
feat: add react loop skeleton
```

## 当前仓库状态

`MyAgent` 已经进入 Phase 2 后的小步稳定阶段。当前状态、最近提交和下一步建议不要写在本文里，统一看：

```text
docs/NEXT_STEPS.md
```

后续提交仍然遵守“模块完成、用户确认后再提交”的节奏。

## 不做什么

当前阶段仍然避免以下工程化复杂度：

- 复杂配置迁移
- 完整权限系统
- 生产级日志平台
- 完整 Web UI
- 大规模插件市场
- 完整 checkpoint/resume

这些内容可以作为后续扩展方向，但不影响第一阶段的核心闭环。
